# Docs index

> Conventions: every doc carries a status line (`current` / `historical record` / `plan`).
> Hand-written docs hold **semantics, invariants, and decisions** — the _why_. The _what_
> (schema columns, route lists) lives in code; docs point at it rather than duplicating it.
> Deleted docs live in git history; we don't keep an archive directory.

- [plans/v4-dashboard-configurator.md](plans/v4-dashboard-configurator.md) — the largest capability gap: there is **no UI to add, remove, reorder or hide a card** — only a hand-written whole-doc `PUT`. Everything it needs already exists (revision-checked write, `hidden` validated + honoured, `NODE_CATALOG` as the picker's data source). Sub-items: `GroupNode.size` is stored but never read, and `TileFeature` has been typed-but-inert through two model generations — wire it or delete it
- [plans/fold-on-the-resolver.md](plans/fold-on-the-resolver.md) — config-v4 built the deterministic per-slot resolver and serves it at `/api/v4/areas/{id}/resolution`, but **no consumer calls it**: the battery-provenance fold still picks inputs by `ordinal` (no unique index) first-wins, and last-wins for grid price. So reordering sources in the Bindings tab changes the report while the fold consumes a different point. Also folds in config-as-producer and the never-done `TariffProvider` generalization
- [plans/availability-to-estimated.md](plans/availability-to-estimated.md) — a missing or stale input should degrade to a **labelled estimate**, never a silent null. `available` currently means only `points.active`; the fold's staleness thresholds exist but as private call-site constants. - [plans/finish-grid-signals-retirement.md](plans/finish-grid-signals-retirement.md) — the card-type half shipped; the load-bearing half did not. `lib/grid/context.ts` still derives the grid device from `area.location`, was _ported forward_ through Phase 13, and now feeds two callers. - [plans/area-point-set-parity-harness.md](plans/area-point-set-parity-harness.md) — [architecture/areas-and-dashboards.md](architecture/areas-and-dashboards.md) asserts that every resolver change is gated by a byte-identical per-area point-set assertion. **Nothing backs that claim** — it was done by hand three times. Also proposes a binding-less fixture area, because the union-default legs have never executed against real data
- [plans/timestamptz-migration.md](plans/timestamptz-migration.md) — migrate time-series time columns to `timestamptz` (needs schema-change approval). Re-verified still-relevant 2026-08-01
- [plans/counter-gap-energy-and-coarse-overlays.md](plans/counter-gap-energy-and-coarse-overlays.md) — the two non-defects left over from the `flow_attr_1d` anomaly hunt, both **research-first**: (a) one missed poll nulls the _next_ interval's `delta` too, so energy that `last` proves flowed is deleted from `agg_1d` — 786 rows/year, count in the short gaps, energy in the long ones; (b) a 30-minute Amber register and a 5-minute Fronius register both decorate `source.grid`, so its overlay is null 5 intervals in 6 and double-counted in the sixth. Carries the measurements, the closed dead end, and a tradeoff table per option. ⚠️ Read §0 before writing code — the `Σ delta` baseline that motivated this is itself the thing that reported three false anomalies
- [plans/ha-parity-and-leapfrog.md](plans/ha-parity-and-leapfrog.md) — **twelve ranked enhancements** measured against Home Assistant, tagged _parity_ (close a real gap: point category, labels, time-weighted means, sub-metering containment, unit classes, generated groups, reauth, composable derivations) or _leapfrog_ (use what HA structurally can't: coverage/confidence surfacing, attribution as a product, a portfolio tier, and pushing recomputed history **into** HA via its statistics-import API). ## Completed plans (as-built records)

Kept because they answer _why does the system look like this_ — not because there is work left in them.

- [plans/completed/chart-library-consolidation.md](plans/completed/chart-library-consolidation.md) — ✅ **COMPLETE 2026-08-01** — **Chart.js → d3**, net −78.9 kB gzip and −83 kB First Load JS on both main routes. Also the record of _how_: the "three chart libraries" claim was doc rot (there were two), an 18-item defect register including a heatmap plugin registered globally and corrupting every other chart in production, and the first automated coverage `components/` has ever had. Read it before touching a chart — especially the sequencing (harness → fix bugs → freeze baseline → port) and the three traps: a screenshot suite can be green because the FIXTURE is wrong, canvas→SVG cannot be pixel-compared (measured floor 5–6 % vs a 0.39 % colour regression), and `useRef` + `useLayoutEffect(…, [])` never measures an element that mounts on a later render
- [plans/completed/config-v4-execution-plan.md](plans/completed/config-v4-execution-plan.md) — ✅ **COMPLETE 2026-08-01** — the **record** of the config-v4 epic: 15 phases, 26 migrations (`0030`→`0055`), 10 days. What was done, what it cost, the decisions that are not recoverable from the code, and the open follow-ups it deliberately did not close. Carries the **Traps and rules** list — read it before touching a migration, a column drop, or a route port
- [plans/completed/config-v4-clean-sheet.md](plans/completed/config-v4-clean-sheet.md) — **the canonical design doc** and the _why_ behind the shipped model: one TypeID space (integer handle retired), `systems`→`devices`, eager areas (tz/location area-only, fixed-offset days endorsed), per-role bindings with deterministic slot resolution, trackers generalized to `derivations`, recursive group/card dashboard docs (tile=small card) with whole-doc PUT + revisions, one share-token semantics. The invariants it locked now live in [architecture/data-model.md](architecture/data-model.md). ⚠️ Carries a **2026-08-01 correction to §4.3** — the resolver shipped, but "used by every consumer" was never true
- [plans/completed/battery-soc-meter-reconciliation.md](plans/completed/battery-soc-meter-reconciliation.md) — the investigation that **disproved a feared data defect**: Daylesford's SoC and its charge/discharge registers do not disagree; the apparent gap is charge-side η + idle drain + BMS recal snaps. Shipped as #169. Read it before assuming a meter is lying
- [plans/completed/battery-provenance-ops-hardening.md](plans/completed/battery-provenance-ops-hardening.md) — two correctness bugs found because a **metrics-only reprice moved an energy total**, which is impossible. That diagnostic move is the reusable part. Part 2's follow-ups are closed out item-by-item in its header (the top-ranked one is moot — `flow_1d` was retired, so there is no legacy view to diverge from)
- [plans/completed/battery-provenance-merge-handoff.md](plans/completed/battery-provenance-merge-handoff.md) — merged as #164, 2026-07-13. The **choreography** a provenance activation needs: deploy, verify the new points self-register, re-backfill ONCE on fixed code, accept against a number. Reuse as the template
- [plans/completed/load-side-run-provenance.md](plans/completed/load-side-run-provenance.md) — ✅ **SHIPPED 2026-08-01** — pricing a CONSUMING device's runs at the fold's **blended load-path intensity** (what the site was drawing on at that moment), so an EV charge session answers "what did that cost?".
