# What this repo does NOT own — the `infra` project

> **Status:** current. Written 2026-09-14 after an agent in this repo proposed creating a BetterStack
> uptime check by hand — first in the dashboard, then with a `curl` — not knowing that the app's
> checks are declared as code in a sibling repo. Both routes would have broken something; see
> [§ Why hand-creating one breaks things](#why-hand-creating-one-breaks-things).
>
> `infra` is a boring infrastructure-as-code repo. It declares the uptime checks, heartbeats and log
> plumbing for several small projects, this one among them, as OpenTofu resources, and it keeps each
> project's operational notes next to the resources they describe. There is nothing to read there
> for application work. The only thing worth knowing is that those resources **have an owner, and it
> is not this repo**.
>
> This doc is a **boundary map, not an inventory.** It records which repo changes what. It carries no
> resource lists, ids or thresholds on purpose — a second copy of those would rot, and they already
> live beside the resources themselves.

## The three repos

| repo | owns |
| --- | --- |
| **`simonhac/LiveOne`** (this one) | the application, its schema and migrations, its Vercel project, the `liveone-flyhub` collector, and the health endpoints the checks call |
| **`simonhac/infra`** | monitoring-as-code: the uptime/keyword checks, heartbeats, log plumbing and their operational notes |
| **`simonhac/the-gitfather`** | the backup/scheduler engine. This repo's `pg-backup.yml` is a thin **caller** of its reusable workflows (profile `pg-backup/liveone.yaml`) |

`infra` uses OpenTofu, **not** Terraform — its state is encrypted client-side and HashiCorp
Terraform cannot read it at all, producing an error that looks like state corruption. Commands go
through its own `scripts/tofu.sh` wrapper.

## The dividing line

Split by **audience**: this repo explains the system; `infra` configures what runs around it.

| belongs in THIS repo | belongs in `infra` |
| --- | --- |
| why the code is shaped this way | what is deployed alongside it, and what is checking it |
| incident post-mortems (the engineering lesson) | the thresholds that came out of one |
| architecture and invariants | resource definitions and their wiring order |
| `.env.tpl` — the `op://` references this app reads | where those values are kept in sync from |

A useful test: *if deleting it would make the **code** harder to understand, it stays here;
otherwise it probably belongs next to the resource it describes.*

## 🛑 Owned by `infra` — don't create or edit these by hand

- **The app's BetterStack checks and heartbeats.** Explicit HCL in `iac/project_liveone.tf`, each
  with the reasoning for its numbers in a comment above it.
- **Log plumbing and metric alerts**, plus the shared log-shipper Fly app. (`infra` owns *that* Fly
  app only — see below for `liveone-flyhub`.)
- **Check and heartbeat *groups***, generated by `for_each` over its manifest.
- **Env-value sync.** Worth knowing as a plain operational fact: the Vercel and Fly env stores are
  sync *targets*, not sources. Setting a value in the Vercel dashboard alone leaves the two
  disagreeing, quietly, until something next syncs.
- **This app's operational notes** — what is checked, the numbers, coverage and known gaps — kept
  next to the resources rather than duplicated here, where they would drift out of date.

## Owned here — `infra` does not do these

- **The app**, its Vercel project and crons (`vercel.json`), and its schema. **Migrations are
  manual** and are not applied at deploy; use `npm run pg-migrate` for prod.
- **`liveone-flyhub`** (`packages/usher`) — deployed **by hand from this repo**, `--ha=false`, every
  time. `infra` manages no part of it. Don't go looking there for the hub, and don't move it there.
- **The health endpoints themselves.** `/api/health`, `/api/health/devices` and their response
  shapes are this repo's code.
  ⚠️ **They are also a contract.** One check asserts on the **body** of `/api/health` (it matches a
  keyword), and others assert exact status codes. Changing a JSON key, changing a status code, or
  making a probe opt-out can leave a check permanently passing — or permanently failing — with **no
  test in this repo going red**. If you change a health response, say so in the PR so the matching
  HCL is updated.
- **This repo's GitHub Actions** (`pg-backup` caller, `sync-prod-to-dev`, `typecheck`, `knip`,
  `preview-alias`) and its committed `.env.tpl`.
- **Incident post-mortems** in `docs/incidents/`.

## Why hand-creating one breaks things

Nothing to do with policy — three mechanical reasons, and the first two have already happened:

- **BetterStack applies `ssl_expiration` and `domain_expiration` per-DOMAIN, not per-monitor**,
  however much the API shape suggests otherwise. A new check on `liveone.energy` created with
  default expiry settings **silently rewrites those settings on every other check for the domain**.
  Proven 2026-09-12: one was given a domain-expiry value and the API applied a different value to
  all three, including one that asked for nothing.
- **Recreating a heartbeat mints a new ping URL**, silently orphaning whatever holds the old one — a
  Vercel env var or Fly secret in *this* repo. The collector keeps running; the heartbeat just never
  hears from it again, so the thing meant to catch a dead collector becomes the thing that goes
  quiet. Every heartbeat there carries `prevent_destroy = true` for exactly this reason.
- **A resource created outside the state file is invisible to it.** The next plan neither manages nor
  reports it, so it sits there unowned and undocumented.

## Working with it

`simonhac/infra` is checked out in its own Conductor workspace alongside this one, with a branch per
workspace exactly like here. Workspace directory names are generated per workspace and change, so
there is no stable path to hardcode — locate it or ask for it.

- **Read first:** `iac/project_liveone.tf` for the resources, and the operational notes it points at
  — its header says to read those before changing any number. Do that.
- **Changing something** means editing the HCL *with* a comment explaining the number, then
  `./scripts/tofu.sh plan -out=tfplan`, reading the plan, then `apply` — and updating the
  operational notes in the same change.
- **🛑 The wrapper fetches credentials at invocation**, so even planning is not a credential-free
  operation. Get explicit consent before running it.
- Saved plans land in `$TMPDIR`, never in the repo. For a durable record keep
  `tofu show -no-color <plan>` output, not the plan file.

## When to reach for `infra` rather than solving it here

- "Add a check / alert / heartbeat for X", or change when something alerts.
- "Why didn't anything catch that?" — its notes already answer this for several classes of failure,
  including the ones deliberately not covered.
- "Add or rotate a value" — it needs to happen where the sync reads from, not only in the Vercel
  dashboard.
- "Wire a heartbeat to a new cron" — the heartbeat is defined there first; only then does its URL
  become an env var here.
